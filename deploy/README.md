# Dev Thriller — Deployment

Two supported targets, both driven from the same Dockerfiles.

## Option A: VPS with Docker Compose

Cheap, simple, single-host. Good for up to a few thousand concurrent users.

1. SSH into your VPS. Install Docker + the compose plugin.
2. Clone this repo; copy `apps/backend/.env` to `./.env.prod` and fill all required fields:
   - `MONGO_URI` — Atlas SRV URI (rotate the password first)
   - `JWT_ACCESS_SECRET` + `JWT_REFRESH_SECRET` — `openssl rand -hex 64`
   - `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`
   - `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `SMTP_PORT`, `SMTP_FROM`
   - `FRONTEND_ORIGIN` — the public URL (`https://app.example.com`)
3. Boot the stack:
   ```
   docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
   ```
4. Put TLS in front. Two easy options:
   - **Caddy** — drop `deploy/Caddyfile` next to the compose file and add a `caddy:` service pointing at it. Caddy handles Let's Encrypt automatically.
   - **Cloudflare Tunnel** — `cloudflared tunnel --url http://localhost:80` and bind it to your DNS record.
5. First-boot housekeeping (run once per new cluster):
   ```
   docker compose -f docker-compose.prod.yml exec backend bun run /app/apps/backend/src/scripts/apply-search-indexes.ts
   ```
6. Put the three workers on cron (host crontab):
   ```
   0 3 * * * cd /opt/dev-thriller && docker compose -f docker-compose.prod.yml run --rm backend bun run /app/apps/workers/src/retention.ts --apply
   0 4 * * * cd /opt/dev-thriller && docker compose -f docker-compose.prod.yml run --rm backend bun run /app/apps/workers/src/audit-verify.ts
   15 5 * * * cd /opt/dev-thriller && docker compose -f docker-compose.prod.yml run --rm backend bun run /app/apps/workers/src/media-extract.ts
   ```

## Option B: Kubernetes

For horizontal scaling, multi-AZ, and rolling deploys.

Manifests live in `deploy/k8s/`:

- `namespace.yaml` — the `dev-thriller` namespace.
- `secrets.example.yaml` — template; **do not commit the real one**. Populate by:
  ```
  kubectl -n dev-thriller create secret generic dt-secrets --from-env-file=apps/backend/.env
  ```
- `dragonfly.yaml` — single-replica StatefulSet with 5Gi PVC. Swap for DragonflyDB Cloud if you prefer managed.
- `backend.yaml` — Deployment + Service + HPA (2–10 pods, 70% CPU target). Readiness uses `/ready`, liveness uses `/health`.
- `frontend.yaml` — Deployment + Service + Ingress (TLS via cert-manager). The nginx config inside the image handles `/v1` + WebSocket proxying.
- `workers-cron.yaml` — three CronJobs (retention, audit-verify, media-extract) reusing the backend image.

Deploy:

```bash
docker build -t ghcr.io/YOUR_ORG/dt-backend:latest -f apps/backend/Dockerfile .
docker build -t ghcr.io/YOUR_ORG/dt-frontend:latest -f apps/frontend/Dockerfile .
docker push ghcr.io/YOUR_ORG/dt-backend:latest
docker push ghcr.io/YOUR_ORG/dt-frontend:latest

kubectl apply -f deploy/k8s/namespace.yaml
kubectl -n dev-thriller create secret generic dt-secrets --from-env-file=apps/backend/.env
kubectl apply -f deploy/k8s/dragonfly.yaml
kubectl apply -f deploy/k8s/backend.yaml
kubectl apply -f deploy/k8s/frontend.yaml
kubectl apply -f deploy/k8s/workers-cron.yaml
```

Then point your DNS at the Ingress controller's LoadBalancer IP. cert-manager provisions the TLS cert automatically on first request.

Run the Atlas Search bootstrap once:

```bash
kubectl -n dev-thriller run atlas-idx --rm -i --restart=Never \
  --image=ghcr.io/YOUR_ORG/dt-backend:latest \
  --env="MONGO_URI=$MONGO_URI" --env="MONGO_DB=devthriller" \
  --command -- bun run /app/apps/backend/src/scripts/apply-search-indexes.ts
```

## Production environment checklist

The backend **refuses to start in production** if any of these are still at default / missing:

- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (must not contain `please_rotate`)
- `MONGO_URI` (must not be `mongodb://localhost`)
- `R2_*` (all three required)

This is enforced in `apps/backend/src/config/env.ts`.

## Observability

- `GET /health` — liveness. Always 200 if the process is running.
- `GET /ready` — readiness. 200 only when Mongo + Dragonfly both respond. Returns a JSON body with per-dependency status + uptime.
- `GET /docs` — Swagger UI, autogenerated from Elysia `t` schemas.
- All responses include an `X-Request-Id` header (incoming one honored when well-formed, otherwise generated). Logs include the same id via Pino child logger.

## Common operations

### Cycle backend pods (zero-downtime)

```bash
# Kubernetes
kubectl -n dev-thriller rollout restart deployment/dt-backend
kubectl -n dev-thriller rollout status deployment/dt-backend

# VPS / Compose
docker compose -f docker-compose.prod.yml up -d --no-deps --build backend
```

The backend's `/ready` endpoint gates the rolling update — pods stay out of rotation until Mongo + Dragonfly both respond.

### Restore from a Mongo Atlas snapshot

1. In Atlas, restore the snapshot to a fresh cluster (or to the same cluster with a new DB name to test first).
2. Update `MONGO_URI` in the secret. K8s: `kubectl -n dev-thriller create secret generic dt-secrets --from-env-file=apps/backend/.env --dry-run=client -o yaml | kubectl apply -f -`. Compose: edit `.env.prod`.
3. Restart the backend (see above).
4. Re-run the Atlas Search bootstrap if you restored to a brand-new cluster:
   ```bash
   bun run /app/apps/backend/src/scripts/apply-search-indexes.ts
   ```

### Rotate JWT or R2 secrets

JWTs are signed with `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET`. Rotating invalidates every active session — plan a maintenance window or do a graceful rotation:

1. Mint the new secret: `openssl rand -hex 64`.
2. Update the env (K8s: rewrite the secret as above; Compose: edit `.env.prod`).
3. Restart the backend.
4. Existing access tokens fail validation on next request, the SPA hits its 401 path and clears the token store, the user re-logs.

R2 keys rotate the same way — update the secret + restart. The presigned URLs minted before the rotation continue to work until they expire (default 15 min for chunk uploads, 1 hour for downloads).

### Drain the thumbnail queue

The thumbnailer pulls a Redis list (`q:thumb`) populated by file uploads. To drain manually after a restore or backlog spike:

```bash
# K8s
kubectl -n dev-thriller create job --from=cronjob/dt-thumbnailer drain-$(date +%s)

# Compose
docker compose -f docker-compose.prod.yml run --rm backend \
  bun run /app/apps/workers/src/thumbnailer.ts --drain
```

The worker exits when the list is empty. Watch the depth with `redis-cli -u $REDIS_URL llen q:thumb` (or `dragonfly-cli`).

### Force a retention sweep

```bash
docker compose -f docker-compose.prod.yml run --rm backend \
  bun run /app/apps/workers/src/retention.ts --apply
```

Without `--apply` the worker dry-runs and prints the count it *would* delete — handy for sanity-checking a new retention setting before letting cron handle it.

### Verify the audit chain

```bash
docker compose -f docker-compose.prod.yml run --rm backend \
  bun run /app/apps/workers/src/audit-verify.ts
```

Exits non-zero if the hash chain is broken. Pipe to your alerting system from cron.
